# 07 - Security review (Phase 7)

Scope: `firestore.rules`, `storage.rules`, the React app, `/functions` (Cloudflare Pages Functions), `/workers` (calendar feed), hosting headers.
Method: read every rule as an attacker who has (a) no account, (b) a portal / calendar token, (c) an account in another company,
(d) a worker login, and read every place where user text becomes an `href`, `src`, CSV cell, ICS line or HTML.
The rules are the security boundary; the browser code is treated as untrusted.

Status: **F** = fixed in this phase, **N** = not fixed (reason given), **OK** = checked, nothing to do.
Every rule fix has automated tests in `rules-tests/` (462 cases, all passing; run `npm run test:rules`), every code fix has a unit or e2e test.

## Checked, nothing to fix

* **Cross-company access.** A member of company A cannot read, list, write or delete anything of company B (companies, all sub-collections, members, invites, leads, portals, public card, calendar feed, users): 100+ cases in `rules.security.test.mjs`. Nested collections under company documents are not matched by any rule (denied).
* **Roles.** Nobody edits their own member document; only the company creator can add themselves as first owner; every other member needs a matching invite for a verified e-mail with the same role and worker link; the creator can never be removed or demoted; admins can only manage workers; workers read only their own tasks/hours/clock/worker record (queries must filter, rules are not filters); `users/{uid}` is self-only (`rules.test.mjs`, `rules.worker.test.mjs`).
* **Billing fields** (`plan`, `subscriptionStatus`, Stripe ids, dates) cannot be created, changed or removed from the browser; only the Stripe webhook (service account) writes them.
* **Portal token.** 24 characters from a 57-symbol alphabet from `crypto.getRandomValues` (about 140 bits). Rules allow `get` only, never `list` or queries, so tokens cannot be enumerated. The portal snapshot is built from an allow-by-strip list (`PORTAL_STRIP`): actual costs, expenses, activity log, crew notes, extra hours, lead source, pay claim and chat are removed; hidden lines travel as numbers only.
* **Calendar token:** same generator; `get` only; the feed holds client names, phones and addresses, so "Make a new link" (rotate) exists in Settings.
* **XSS.** No `eval`/`innerHTML`. `dangerouslySetInnerHTML` appears in four places (`ui/Icon.tsx`, `components/KpiCard.tsx`, `pages/public/LeadForm.tsx` svg helper, doc comment in `design/icons.ts`), all fed by constant icon path strings from `src/design/icons.ts`, never by user data. All user text is rendered by React (escaped).
* **Deep links** (`wa.me`, `sms:`, `tel:`, `mailto:`, Google Calendar, maps): phone numbers are reduced to digits, text is `encodeURIComponent`-ed.
* **Secrets.** `.env*` and `.dev.vars` are ignored by git; no Stripe or service-account keys in the repo (`git grep`); the browser stores no secret in localStorage (only theme, language, last tab, last backup time; demo mode aside). Console logging only prints error objects (no client data).
* **Cloudflare functions.** Firebase ID token fully verified (RS256 against Google keys, `kid`, `exp`, `iat`, `aud`, `iss`, `sub`); owner role re-checked in Firestore with the service account; ids validated (`isSafeId`); Stripe webhook signature verified over the raw body with a time window and constant-time compare; CORS is **off** unless `ALLOWED_ORIGIN` is set and then only that exact origin; unexpected errors return a generic message (details only in the log); all responses `no-store`. `success_url` / `return_url` are built from `APP_URL` (validated) or the request's own origin.
* **Calendar worker** (`workers/calendar-feed.js`): GET/HEAD only, token pattern `[A-Za-z0-9]{16,64}`, reads one document; now also sends `X-Content-Type-Options: nosniff`.

## Things the owner must do (cannot be done in code)

1. Publish `firestore.rules` and `storage.rules` after every change (`docs/09-deploy-cloudflare.md`, step 5) and run `npm run test:rules` first.
2. Turn on **App Check** for Firestore / Storage before advertising the request form widely.
3. Restrict the Firebase Web API key to your domains (Google Cloud console > APIs & Services > Credentials).
4. In Firebase Authentication turn on **email enumeration protection** and consider a 8+ character password policy (the app only asks for 6).
5. Blaze plan (needed for Storage): set a **budget alert**.
6. Keep the calendar link private; rotate it from Settings if it was shared by mistake.

## How the CSP was verified

`npm run build`, `node e2e/serve-dist.mjs` (serves `dist/` and applies the rules of `public/_headers` like Cloudflare Pages does), then Playwright drives the flows above and fails on any `securitypolicyviolation` event or console error (`npm run test:e2e -- --project=csp`). A second test proves the policy is actually enforced (an injected inline script and a foreign image are blocked).
Not testable here (no real Firebase project): the exact hosts used by the Firebase SDK in real mode. The policy allows `firestore.googleapis.com`, `firebasestorage.googleapis.com`, `identitytoolkit.googleapis.com`, `securetoken.googleapis.com`, `www.googleapis.com` and `*.firebaseio.com`. If the browser console on the deployed site shows "Refused to connect to ...", add that host to `connect-src` in `public/_headers` (the launch checklist has this step). `frame-src 'none'` would need a change if Google sign-in popups or the reCAPTCHA (App Check) widget are added (`https://www.google.com`, `https://apis.google.com`).
